1 · Arena swipe

The room is laid out in a different order than the tabs

The tabs run Home, Analytics, History, Library, Profile. The room runs History, Home and Analytics together, the coach's corner, Library, Profile. Every swipe walks the camera to the place's spot in the room, so the swipe direction and the camera direction only agree when the two orders happen to line up. That explains everything you saw:

  • Home and Analytics share one spot, so the room stays still.
  • History is at the far left, so going Analytics to History walks the camera backward.
  • Library is three spots to the right of History, so the camera crosses the whole room.
  • Library to Profile are neighbours in both orders, which is why that one feels right.

The frame is the phone's view of the room: about 103 room pixels wide, roughly one place per screen. To go to the next tab your finger moves left, so the room should slide left too, which means the camera steps right.

What's on it

  • The week strip and workout count stay. They're Home's own and they work.
  • Due (off by default, add it in Customize): muscles you haven't trained the longest. The engine already computes days since last per muscle; Analytics only uses it on the arena board.
  • Beat last time (on by default): for your next workout (the block's Up Next day, or the template you run most), the last top set per lift and one small step up. This uses the "last time" engine the logger already has.
  • PRs this week stay, as the celebration line.
  • Top set and Top gain leave Home. Analytics keeps them.

The smaller option: keep the card as it is and only swap Top set and Top gain for "Due" and "PRs this week". About half the work, and less useful.

One thing I noticed in your data: Leg Extensions 160 × 66 on Nov 17. That's probably meant to be 6 reps. The analytics treat it as real, so it's worth fixing in History.
3 · Block analytics

Analytics that only count the block's workouts

Every workout started from a block already stores which run, week and day it belongs to, and keeps a copy of the plan it was started from. So the block view can count only those workouts, measured in block weeks (W1 to W8) instead of calendar weeks. Workouts logged on the side don't mix in. The regular Analytics view stays as it is.

How it works

  • Where: a scope chip at the top of Analytics, "All training" or the block's name. It shows while a block is running, and past blocks can be picked too. The block's own page and the Up Next card on Home link straight to it.
  • Same views, same feel: Muscles, Strength, Exercises and Execution with the same tabs, cascade, count-ups and chart draw-ins. Inside a block they read in block weeks.
  • New, block only: the progress ring, sets logged against the plan per week, the planned line on each lift's chart, and the gain since week 1.
  • Arena: while the block scope is on, the scoreboard can show the block's week grid. The rack's program board already draws it, so this is optional polish.

Taken from your RecoveryProgram logbook

  • The x-axis in program weeks, not dates
  • "Sets logged, of prescribed" bars per week
  • Left and right as separate lines for per-side lifts
  • A crosshair with a tooltip on every chart, and "Show numbers" under it

Left behind on purpose: its flat styling and the symptom and gate tracking. LogChamp's look and motion carry over unchanged. The charts are drawn in LogChamp's tokens, so they work in every palette.

Under the hood

New pure function blockSummary() in server/src/analytics/, fixture-tested like the rest of the engine. It reuses the summary, plan-vs-actual and PR functions, filtered to one run and grouped by blockWeekOrder. New route GET /analytics/block-run/:id, scoped to the signed-in user: someone else's run returns 404. That cross-user check is the one security surface in this wave, and I'll read it myself at the gate.
